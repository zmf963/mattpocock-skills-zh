## 它做什么

`triage` 将你项目跟踪器上的 issues 移过一个小的分类角色**状态机**——对它们进行分类、验证声明、在需要时通过追问使其成型，并留下 ready-for-agent 的简报。

它从不盲目贴标签。每个已分类的项目携带恰好一个**类别**角色（`bug` / `enhancement`）和一个**状态**角色（`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`），并且它*建议并等待*——它告诉你它的类别和状态判断并附上推理，然后仅在你的指示下行动。在任何东西被提升到 `ready-for-agent` 之前，它首先验证声明：bug 被复现，PR 被检出并运行。

## 何时使用它

你通过输入 `/triage` 并用自然语言描述你想要什么来调用它——agent 不会自行调用它。"显示我需要关注的任何东西"、"让我们看看 #42"、"将 #42 移至 ready-for-agent"。

当你的问题跟踪器有原始的、未经评估的报告，并且你想要它们被排序、验证并转化为 agent 或人类可以领取的工作时使用它。要将确定的对话转化为新的 spec，改用 [to-prd](https://aihero.dev/skills-to-prd)；要将现有 PRD 分解为工单，使用 [to-issues](https://aihero.dev/skills-to-issues)。`triage` 是相反的方向——它处理*已经*落在跟踪器中的东西。

## 前置条件

`triage` 读取和写入你的问题跟踪器，因此 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 必须首先配置了跟踪器和标签映射。上面的角色名称是**规范**的——你跟踪器中的实际标签字符串可能不同，该映射就是 setup 提供的东西。配置还决定了外部 PR 是否算作请求面，以及谁算作外部。

## PR 是附带代码的 issue

当跟踪器将外部 pull requests 视为请求面时，`triage` 通过*相同*的机器运行它们：相同的类别角色、相同的状态、相同的转换——状态只是针对 diff 而非报告来解读。`ready-for-agent` 意味着附加了简报，agent 应在代码上采取下一步；`ready-for-human` 意味着它已准备好合并。发现仅显示外部 PR，但显式命名的 PR 无论作者是谁都会被分类。

## 先验证，再简报

将 `triage` 与随意贴标签分开的步骤是验证。它从报告者的步骤复现 bug，或检出 PR 并运行测试，并报告回来：以代码路径确认、失败或细节不足（这本身就是一个强烈的 `needs-info` 信号）。它还运行两个代码库检查——**冗余**（这已经实现了吗？那么是 `wontfix`）和**先前拒绝**（`.out-of-scope/` 已经说不了吗？）。确认的验证产生更强得多的 agent 简报；猜测不会。

## 它在正常工作的标志

- 它接触的每个项目以恰好一个类别角色和一个状态角色结束——从不是零个，从不是两个冲突的状态。
- 它交给你一个附有推理的建议并等待，而不是自行重新贴标签。
- Bug 被复现，PR 被运行，在任何东西到达 `ready-for-agent` 之前。
- 它发布到跟踪器的每条评论以 `> *This was generated by AI during triage.*` 免责声明开头。

## 它在哪里

`triage` 是你问题跟踪器的**周期性维护**环节——每当报告堆积时运行它，以保持队列有序且 `ready-for-agent` 列可信。它位于跟踪器的前端，构建链的上游：它写的简报是 [tdd](https://aihero.dev/skills-tdd) 后来领取以实现的东西。当请求需要锐化时，它依赖 [grilling](https://aihero.dev/skills-grilling) 和 [domain-modeling](https://aihero.dev/skills-domain-modeling) 一次一个问题地将其追问成型。它最近的邻居是 [to-prd](https://aihero.dev/skills-to-prd)，它从新对话填充跟踪器，而 `triage` 处理已经存在的东西。当你不确定哪个 skill 或流程适合时，[ask-matt](https://aihero.dev/skills-ask-matt) 为你路由。
