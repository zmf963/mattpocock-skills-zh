# To Tickets

将计划、spec 或对话拆分为一组**票据**——曳光弹式的垂直切片，每张声明**阻塞**它的票据。

issue 跟踪器和 triage 标签词汇表应该已经提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容工作。如果用户传入一个引用（spec 路径、issue 编号或 URL）作为参数，获取它并读取其完整正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索过代码库，请探索以了解代码的当前状态。票据标题和描述应使用项目的领域词汇表术语，并尊重你触及区域中的 ADR。

寻找预重构代码以简化后续实现的机会。"让变更变得容易，然后做出容易的变更。"

### 3. 草拟垂直切片

将工作拆分为**曳光弹**票据。

<vertical-slice-rules>

- 每个切片是一条狭窄但完整的路径，贯穿每一层（schema、API、UI、tests）——垂直的，不是单层的水平切片
- 完成的切片可以独立演示或验证
- 每个切片大小适合单个全新的上下文窗口
- 任何预重构应该先做

</vertical-slice-rules>

为每张票据注明其**阻塞边**——必须在它开始之前完成的其他票据。没有阻塞者的票据可以立即开始。

**宽重构是垂直切片的例外。** **宽重构**是一种机械性变更——重命名一个列、变更一个共享符号的类型——其**影响范围**遍布整个代码库，一次编辑就破坏数千个调用点，没有垂直切片能独立通过。不要强行把它塞进曳光弹；将其编排为**展开——收缩**。首先展开：在旧形式旁边添加新形式，这样什么都不会破坏。然后按影响范围分批迁移调用点（每个包、每个目录），每批是一张被展开票据阻塞的独立票据，批次之间保持 CI 绿色，因为旧形式仍然存在。最后收缩：在没有任何调用者后删除旧形式，于一张被每个迁移批次阻塞的票据中完成。当即使批次也无法独立保持绿色时，保持这个顺序但让它们共享一个集成分支，所有批次都阻塞一张最终的集成验证票据——只有在那一张那里才承诺绿色。

### 4. 询问用户

将提议的拆解呈现为编号列表。每张票据展示：

- **标题**：简短的描述性名称
- **被阻塞于**：哪些其他票据（如果有）必须先完成
- **它交付什么**：这张票据实现的端到端行为

询问用户：

- 粒度感觉合适吗？（太粗/太细）
- 阻塞边正确吗——每张票据只依赖真正卡住它的票据？
- 有没有票据应该合并或进一步拆分？

迭代直到用户批准这个拆解。

### 5. 将票据发布到配置的跟踪器

发布批准的票据。**如何**发布取决于 `/setup-matt-pocock-skills` 配置的跟踪器——无论哪种方式，票据相同，只有阻塞边的形状不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每张票据写一个文件，从 `01` 开始按依赖顺序编号（阻塞者在前）。每个文件的"被阻塞于"列出它所依赖的编号/标题。使用下面的单票据文件模板——每张票据一个文件，永远不是一个合并文件。
- **真正的 issue 跟踪器（GitHub、Linear……）** → 按依赖顺序（阻塞者在前）为每张票据创建一个 issue，这样每张票据的阻塞边可以引用真实的标识符。使用平台的原生阻塞/子 issue 关系（如果有）；否则将每张票据的"被阻塞于"设置为阻塞它的 issue。应用 `ready-for-agent` triage 标签，除非另有指示——这些票据本身就是 agent 可以接的。

处理**前沿**：阻塞者全部完成的任何票据。对于纯线性链条，这意味着从上到下。

不要关闭或修改任何父 issue。
