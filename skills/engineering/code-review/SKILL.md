对 `HEAD` 与用户提供的固定点之间的 diff 进行双轴审查：

- **标准**（Standards）— 代码是否符合此仓库文档化的编码标准？
- **规格**（Spec）— 代码是否忠实地实现了原始 issue / PRD / 规格？

两个轴作为**并行的子 agent** 运行，这样它们不会污染彼此的上下文，然后此技能汇总它们的发现。

issue 追踪器应该已经提供给你了 —— 如果 `docs/agents/issue-tracker.md` 缺失，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户说的任何内容就是固定点 —— 一个 commit SHA、分支名、tag、`main`、`HEAD~5` 等。如果他们没有指定，询问他们。

一次性捕获 diff 命令：`git diff <fixed-point>...HEAD`（三点，这样比较是针对 merge-base 的）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

在继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`）且 diff 非空。错误的引用或空的 diff 应在此处失败 —— 而不是在两个并行子 agent 内部。

### 2. 识别规格来源

按以下顺序查找原始规格：

1. commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）—— 通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下匹配分支名或功能的 PRD/spec 文件。
4. 如果什么都没找到，询问用户规格在哪里。如果他们说没有，**Spec** 子 agent 将跳过并报告"无可用规格"。

### 3. 识别标准来源

仓库中任何文档化了代码应如何编写的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库文档化的内容之外，标准轴始终携带下面的**坏味道基线**（smell baseline）—— 一组固定的 Fowler 代码坏味道（*《重构》*，第 3 章），即使仓库没有文档化任何内容也适用。两条规则约束它：

- **仓库优先。** 文档化的仓库标准始终胜出；当它认可基线会标记的内容时，抑制该坏味道。
- **始终是判断。** 每个坏味道是一个带标签的启发式（"可能的 Feature Envy"），绝不是硬性违规 —— 并且，像这里的任何标准一样，跳过工具链已经强制执行的任何内容。

每个坏味道读作*它是什么* → *如何修复*；将其与 diff 匹配：

- **神秘命名**（Mysterious Name）— 一个函数、变量或类型，其名称不揭示它做什么或持有什么。→ 重命名它；如果没有诚实的名称出现，设计就有问题。
- **重复代码**（Duplicated Code）— 相同的逻辑形状出现在变更中的多个 hunk 或文件中。→ 提取共享的形状，从两处调用它。
- **依恋情结**（Feature Envy）— 一个方法访问另一个对象的数据比访问自己的还多。→ 将该方法移到它所依恋的数据上。
- **数据泥团**（Data Clumps）— 相同的几个字段或参数总是一起出现（一个想要诞生的类型）。→ 将它们捆绑成一个类型，传递那个。
- **基本类型偏执**（Primitive Obsession）— 一个基本类型或字符串在代替一个值得拥有自己类型的领域概念。→ 给该概念一个自己的小类型。
- **重复的 Switch**（Repeated Switches）— 对同一类型的相同 `switch`/`if` 级联在变更中重复出现。→ 用多态替换，或一个两个地方共享的 map。
- **霰弹式修改**（Shotgun Surgery）— 一个逻辑变更迫使在 diff 中的许多文件中进行分散的编辑。→ 将一起变更的东西聚集到一个模块中。
- **发散式变更**（Divergent Change）— 一个文件或模块因为几个不相关的原因被编辑。→ 拆分以使每个模块因为一个原因变更。
- **夸夸其谈的未来性**（Speculative Generality）— 为规格没有的需求添加的抽象、参数或钩子。→ 删除它；内联回去，直到真正的需求出现。
- **消息链**（Message Chains）— 调用者不应依赖的长链 `a.b().c().d()` 导航。→ 将遍历隐藏在第一个对象的一个方法后面。
- **中间人**（Middle Man）— 一个类或函数大部分只是转发委托。→ 删除它，直接调用真正的目标。
- **拒绝的遗赠**（Refused Bequest）— 一个子类或实现者忽略或覆盖了它继承的大部分内容。→ 放弃继承，使用组合。

### 4. 并行启动两个子 agent

发送一条带有两个 `Agent` 工具调用的消息。对两个都使用 `general-purpose` 子 agent。

**标准子 agent 提示** — 包含：

- 完整的 diff 命令和 commit 列表。
- 你在第 3 步中找到的标准源文件列表，**加上第 3 步的坏味道基线**完整粘贴 —— 子 agent 没有其他途径访问它。
- 简报："报告 —— 在相关的每个文件/hunk 中 —— (a) diff 违反文档化标准的每一处：引用标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：命名它并引用 hunk。区分硬性违规和判断 —— 文档化标准的违反可以是硬性的，但基线坏味道始终是判断，并且文档化的仓库标准会覆盖基线。跳过工具链强制执行的任何内容。400 词以内。"

**规格子 agent 提示** — 包含：

- diff 命令和 commit 列表。
- 规格的路径或获取的内容。
- 简报："报告：(a) 规格要求但缺失或不完整的需求；(b) diff 中存在但未被要求的行为（范围蔓延）；(c) 看起来已实现但实现看起来有误的需求。为每个发现引用规格行。400 词以内。"

如果规格缺失，跳过 Spec 子 agent 并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下呈现两份报告，逐字或略微清理。**不要**合并或重新排序发现 —— 两个轴是故意分离的（参见*为什么是两个轴*）。

以一行摘要结束：每个轴的发现总数，以及每个轴内最严重的问题（如果有）。不要跨轴选出单一的赢家 —— 那正是分离所要防止的重新排序。

## 为什么是两个轴

一个变更可以通过一个轴而失败于另一个轴：

- 代码遵循所有标准但实现了错误的东西 → **标准通过，规格失败。**
- 代码完全按照 issue 的要求做但违反了项目的约定 → **规格通过，标准失败。**

分开报告它们阻止了一个轴掩盖另一个轴。
