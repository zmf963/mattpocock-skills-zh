# Test-Driven Development

TDD 是 red → green 循环。此技能是使该循环产生值得保留的测试的参考：什么是一个好的测试、测试放在哪里、反模式以及循环的规则。每个部分在每个循环上都适用 —— 在循环之前和期间查阅它们，而不是之后。

探索代码库时，读取 `CONTEXT.md`（如果存在）以便测试名称和接口词汇匹配项目的领域语言，并尊重你正在接触的区域的 ADR。

## 什么是好的测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。一个好的测试读起来像一个规格说明 —— "user can checkout with valid cart" 精确地告诉你什么能力存在 —— 并且在重构中存活，因为它不关心内部结构。

参见 [tests.md](tests.md) 获取示例，[mocking.md](mocking.md) 获取 mock 指南。

## Seam —— 测试放在哪里

**接缝**（seam）是你测试的公共边界：你在不触及内部的情况下观察行为的接口。测试存在于 seam 处，永远不对内部。

**仅在预先商定的 seam 处测试。** 在编写任何测试之前，写下要测试的 seam 并与用户确认。没有测试在未确认的 seam 处编写。你无法测试一切 —— 提前商定 seam 是测试努力如何落在关键路径和复杂逻辑上而不是每个边缘情况上的方式。

问："公共接口是什么，我们应该在哪些 seam 处测试？"

## 反模式

- **与实现耦合** — mock 内部协作者、测试私有方法、或通过侧信道验证（查询数据库而不是使用接口）。标志：测试在重构时破坏但行为没有改变。
- **同义反复** — 断言以代码计算的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`，以同样方式手工推导的快照，一个常量断言等于自身），因此它通过构造就能通过，永远不可能与代码不一致。预期值必须来自独立的真相来源 —— 一个已知良好的字面量、一个工作示例、规格。
- **水平切片** — 先写所有测试，然后所有实现。批量测试验证*想象*的行为：你测试事物的*形状*而不是面向用户的行为，测试对真实变化变得不敏感，并且你在理解实现之前就承诺了测试结构。改为以**垂直切片**工作 —— 一个测试 → 一个实现 → 重复，每个测试是一个**示踪子弹**（tracer bullet），响应上个循环教给你的东西。

## 循环规则

- **Red 在 green 之前。** 先写失败的测试，然后仅写足够的代码使其通过。不要预期未来的测试或添加推测性功能。
- **一次一个切片。** 每个循环一个 seam，一个测试，一个最小实现。
- **重构不是循环的一部分。** 它属于审查阶段（参见 `review` 技能），而不是 red → green 实现循环。
