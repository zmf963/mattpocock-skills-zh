# Prototype

一个原型是**回答一个问题的一次性代码**。问题决定形状。

## 选择分支

识别正在回答哪个问题 —— 从用户的提示、周围的代码，或如果用户在附近则询问：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个小的交互式终端应用，将状态机推过难以在纸面上推理的情况。
- **"这应该长什么样？"** → [UI.md](UI.md)。在单个路由上生成几个根本不同的 UI 变体，通过 URL 搜索参数和浮动底栏可切换。

两个分支产生非常不同的产物 —— 搞错这一点会浪费整个原型。如果问题确实模糊且用户不可达，默认选择更匹配周围代码的分支（后端模块 → logic；页面或组件 → UI）并在原型顶部陈述假设。

## 两者都适用的规则

1. **从一开始就是一次性的，并明确标记。** 将原型代码放在它实际将被使用的地方附近（在它为之制作原型的模块或页面旁边），这样上下文是明显的 —— 但要命名它，使偶然的读者能看到它是一个原型，而不是生产代码。对于一次性 UI 路由，遵循项目已有的任何路由约定；不要发明新的顶层结构。
2. **一个命令运行。** 无论项目现有的任务运行器支持什么 —— `pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够无需思考地启动它。
3. **默认无持久化。** 状态存在于内存中。持久化是原型正在*检查*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，使用一个临时数据库或本地文件，带有清晰的"PROTOTYPE — wipe me"名称。
4. **跳过润色。** 没有测试，没有超出使原型*可运行*的错误处理，没有抽象。关键是快速学习然后删除它。
5. **展示状态。** 每次操作后（logic）或每次变体切换时（UI），打印或渲染完整的相关状态，这样用户可以看到什么改变了。
6. **完成后删除或吸收。** 当原型回答了它的问题时，要么删除它，要么将验证过的决策折叠到真实代码中 —— 不要让它烂在仓库里。

## 完成后

*答案*是原型中唯一值得保留的东西。将它捕获到某个持久的地方（commit 消息、ADR、issue 或原型旁边的 `NOTES.md`）以及它正在回答的问题。如果用户在附近，捕获就是一次快速对话；如果不在，留下占位符，这样他们（或你，在下次经过时）可以在删除原型之前填写结论。
