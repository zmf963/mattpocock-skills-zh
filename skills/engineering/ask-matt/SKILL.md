# Ask Matt

你不会记住每个技能，所以来问吧。

**流程**（flow）是一条穿越技能的路径。大多数路径沿一条**主流程**（main flow）运行，两条**入口匝道**（on-ramps）汇入其中。其余的都是独立技能，或者是在底层运行的词汇层。

## 主流程：idea → ship

大多数工作所经过的路径。你有一个想法，并想要构建它。

1. **`/grill-with-docs`** — 通过访谈来打磨想法。当你**有一个代码库**时从这里开始：它是有状态的，会在 `CONTEXT.md` 和 ADR 中保留它学到的东西。（没有代码库？使用 `/grill-me` — 参见独立技能。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是会留下书面记录的那个。）
2. **分支 — 你能在对话中解决每个问题吗？** 如果一个问题需要可运行的答案（状态、业务逻辑、你必须看到的 UI），通过原型来绕道，由 **`/handoff`** 在两个方向上桥接（参见跨会话）：
   - **`/handoff`** 转出，然后针对该文件打开一个新会话，
   - **`/prototype`** 用一次性代码来回答问题，
   - **`/handoff`** 转回你学到的东西，并从原始想法线程中引用它。
3. **分支 — 这是多会话构建吗？**
   - **是** → **`/to-prd`**（将线程转化为 PRD）→ **`/to-issues`**（将 PRD 拆分为可独立领取的 issue）。由于 issue 是独立的，**在每个 issue 之间清除上下文**：为每个 issue 启动一个全新会话，并通过传入 PRD 和要处理的单个 issue 来启动 **`/implement`**。
   - **否** → **`/implement`** 就在这里，在同一个上下文窗口中。

   无论哪种方式，**`/implement`** 通过内部驱动 **`/tdd`** 来构建每个 issue —— 一次一个红-绿切片 —— 然后在提交之前通过运行 **`/code-review`**（一个对 diff 的双轴审查：标准 + 规格）来收尾。当你只想在没有完整规格的情况下测试先行地构建一个具体行为时，可以单独使用 **`/tdd`**；当你想针对一个固定点审查一个分支或 PR 时，可以单独使用 **`/code-review`**。

### 上下文卫生

将步骤 1-3 保持在**一个不间断的上下文窗口**中 —— 在 `/to-issues` 之前不要压缩或清除 —— 这样 grilling、PRD 和 issue 都建立在相同的思考之上。然后每个 `/implement` 从全新开始，基于 issue 来工作。

对此的限制是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口（在最先进模型上约 120k token）。如果会话在 `/to-issues` 之前接近该限制，不要在被降级的推理上勉强推进 —— 使用 `/handoff` 并在新线程中继续。

## 入口匝道

一种产生工作的起始情况，然后汇入主流程。

- **Bug 和请求堆积** → **`/triage`**。它将 issue 通过 triage 角色移动，并产生 agent 就绪的 issue，稍后由 **`/implement`** 接手。

  Triage 仅用于**不是你创建的** issue —— bug 报告、传入的功能请求、任何原始到达的东西。`/to-issues` 产生的 issue 已经是 agent 就绪的，所以**不要对它们进行 triage**。

- **某些东西坏了** → **`/diagnosing-bugs`**。用于难解的 bug：抗拒第一眼检查的 bug、间歇性 flake、在两个已知良好状态之间悄悄出现的回归。它在拥有一个**紧密的反馈循环**之前拒绝进行理论化 —— 一个已经在此 bug 上变红（red）的命令 —— 然后用回归测试修复。当事后发现没有好的 seam 来锁定 bug 时，其事后分析会转交给 **`/improve-codebase-architecture`**。

## 代码库健康

不是功能工作 —— 维护。

- **`/improve-codebase-architecture`** — 有空闲时间时运行，以保持代码库适合 agent 操作。它揭示**深化机会**（deepening opportunities）；选择一个*会产生一个想法*，你可以在 `/grill-with-docs` 将其带入主流程。它是发现候选方案的调查；**`/codebase-design`**（如下）是你设计所选方案的工作台。

## 底层词汇

两个模型调用的参考，在*其他技能之下*运行 —— 每个都是其词汇的单一真相来源。当**词语**而非流程是问题时，直接使用它们；或让上面的技能来拉入它们。

- **`/domain-modeling`** — 打磨项目的*领域*语言：挑战模糊术语，解决过载词汇（一个 "account" 做三件事），将难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动的主动纪律，用于保持 `CONTEXT.md` 是一个干净的词汇表。
- **`/codebase-design`** — 深度模块词汇（module、interface、depth、seam、adapter、leverage、locality），用于设计模块的*形状*：在一个干净 seam 处、大量行为隐藏在小接口之后。`/tdd` 和 `/improve-codebase-architecture` 都使用它。

## 跨会话

- **`/handoff`** — 当线程已满或你需要分支出去（例如进入 `/prototype` 会话），此技能将对话压缩为 markdown 文件。你不会在原地继续 —— 你**打开一个新会话并引用该文件**以跨上下文窗口传递上下文。它是上下文窗口之间的桥梁，双向皆可。当你想获得**全新会话**但需要**保留当前对话**时使用它。
- **`/compact`**（内置）— 留在**同一对话**中，让前面的轮次被总结。在**阶段之间的有意断点**使用它，当你不介意丢失逐字历史时。不要在阶段中途压缩 —— agent 可能会迷失方向。`/handoff` 是分叉；`/compact` 是继续。

## 独立技能

完全脱离主流程。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的不懈访谈，但适用于**没有代码库**的情况。无状态：它不在本地保存任何东西，不构建 `CONTEXT.md`。用它来打磨任何不存储在仓库中的计划或设计。
- **`/prototype`** — 一个小型、一次性的程序，用于回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。从一开始就是一次性的 —— 保留答案，删除代码。它是主流程第 2 步中的绕道，但任何时候当设计问题难以在纸面上解决时都可以使用它。
- **`/research`** — 将阅读跑腿工作委托给**后台 agent**：它根据**一手来源**调查一个问题，然后在仓库中留下一个带引用的 Markdown 文件。在它阅读时你继续工作。它产生的文件是带入主流程 `/grill-with-docs` 的东西 —— 研究为思考提供素材，而不是替代思考。
- **`/teach`** — 在多个会话中学习一个概念，使用当前目录作为有状态的工作区。
- **`/writing-great-skills`** — 编写和编辑技能的参考。

## 前置条件

**`/setup-matt-pocock-skills`** — 在第一次工程流程之前运行，以配置 issue 追踪器、triage 标签和其他技能所假设的文档布局。自定义 issue 追踪器也能用。
