# Diagnosing Bugs

一个用于难解 bug 的纪律。仅在明确有理由时跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型，并检查你正在接触的区域的 ADR。

## 阶段 1 — 构建反馈循环

**这就是这项技能。** 其他一切都是机械的。如果你有一个针对 bug 的**紧密**（tight）通过/失败信号 —— 一个在*此* bug 上变红（red）的信号 —— 你就会找到原因；二分法、假设测试和插桩都只是消耗它。如果你没有，再多的代码审视也救不了你。

在此处花费不成比例的努力。**要激进。要有创意。拒绝放弃。**

### 构建方法 —— 大致按此顺序尝试

1. **失败的测试**，在能达到 bug 的任何 seam 处 —— 单元、集成、端到端。
2. **Curl / HTTP 脚本**，针对运行中的开发服务器。
3. **CLI 调用**，使用固定输入，将 stdout 与已知良好的快照进行 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，对 DOM/console/network 进行断言。
5. **重放捕获的跟踪。** 将真实的网络请求 / 有效载荷 / 事件日志保存到磁盘；在隔离中通过代码路径重放它。
6. **一次性 harness。** 启动系统的最小子集（一个服务，mock 依赖），用单个函数调用执行 bug 代码路径。
7. **属性 / fuzz 循环。** 如果 bug 是"有时输出错误"，运行 1000 个随机输入并寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态（commit、数据集、版本）之间，自动化"在状态 X 启动，检查，重复"，这样你可以 `git bisect run` 它。
9. **差分循环。** 通过旧版本 vs 新版本（或两个配置）运行相同输入，并 diff 输出。
10. **HITL bash 脚本。** 最后的手段。如果必须有人点击，用 `scripts/hitl-loop.template.sh` 驱动*他们*，这样循环仍然是结构化的。捕获的输出反馈给你。

构建正确的反馈循环，bug 就 90% 修复了。

### 收紧循环

将循环视为产品。一旦你有了*一个*循环，**收紧**它：

- 我能让它更快吗？（缓存设置，跳过无关初始化，缩小测试范围。）
- 我能让信号更敏锐吗？（断言具体症状，而不是"没有崩溃"。）
- 我能让它更确定性吗？（固定时间，种子 RNG，隔离文件系统，冻结网络。）

一个 30 秒的不稳定循环几乎不比没有循环好；一个 2 秒的确定性循环是紧密的 —— 一种调试超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。循环触发 100 次，并行化，增加压力，缩小时间窗口，注入 sleep。一个 50% flake 的 bug 是可调试的；1% 不是 —— 不断提高比率直到它可调试。

### 当你确实无法构建循环时

停下来并明确说明。列出你尝试了什么。向用户请求：(a) 访问任何能复现它的环境，(b) 一个捕获的产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产插桩的权限。在拥有循环之前**不要**继续进行假设。

### 完成标准 —— 一个能变红的紧密循环

当循环是**紧密的**且**能变红的**（red-capable）时，阶段 1 完成：你能说出**一个命令** —— 一个脚本路径、一个测试调用、一个 curl —— 你已经**至少运行过一次**（粘贴调用及其输出），并且它是：

- [ ] **能变红的** — 它驱动实际的 bug 代码路径并断言**用户的确切症状**，因此它能在此 bug 上变红，修复后变绿。不是"运行不出错"—— 它必须能够*捕获这个特定的 bug*。
- [ ] **确定性的** — 每次运行相同的判定（flaky bug：固定的高复现率，如上所述）。
- [ ] **快速的** — 几秒，不是几分钟。
- [ ] **Agent 可运行的** — 你可以无人值守地运行它；仅在通过 `scripts/hitl-loop.template.sh` 时才有人在循环中。

如果你发现自己在构建理论之前阅读代码，而这个命令还不存在，**停下来 —— 直接跳到假设正是这项技能所要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。观察它变红 —— bug 出现了。

确认：

- [ ] 循环产生了**用户**描述的失败模式 —— 不是恰好发生在附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者，对于非确定性 bug，以足够高的比率可复现来进行调试）。
- [ ] 你已捕获确切症状（错误消息、错误输出、缓慢的时间），以便后续阶段可以验证修复确实解决了它。

### 最小化

一旦它变红，将复现缩小到**仍能变红的最小场景**。**一次一个**地削减输入、调用者、配置、数据和步骤，每次削减后重新运行循环 —— 只保留对失败有负载支撑作用的。

为什么费这个事：最小复现缩小了阶段 3 中的假设空间（更少的移动部件需要怀疑），并成为阶段 5 中的干净回归测试。

当**每个剩余元素都是负载支撑的**时完成 —— 移除其中任何一个都会使循环变绿。

在复现**且**最小化之前不要继续。

## 阶段 3 — 假设

在测试任何假设之前生成 **3-5 个排名的假设**。单个假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**（falsifiable）：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失 / <改变 Z> 会使它更糟。"

如果你不能陈述预测，这个假设就是一种感觉 —— 丢弃或打磨它。

**在测试之前向用户展示排名的列表。** 他们通常拥有能立即重新排名的领域知识（"我们刚刚部署了对 #3 的更改"），或者知道他们已经排除的假设。廉价的检查点，巨大的时间节省。不要阻塞于此 —— 如果用户 AFK，按你的排名继续。

## 阶段 4 — 插桩

每个探针必须映射到阶段 3 的特定预测。**一次改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **针对性日志**，在能区分假设的边界处。
3. 永远不要"记录一切然后 grep"。

**用唯一前缀标记每个调试日志**，例如 `[DEBUG-a4f2]`。最后的清理变成单个 grep。未标记的日志存活；标记的日志死亡。

**性能分支。** 对于性能回归，日志通常是错误的。相反：建立基线测量（计时 harness、`performance.now()`、分析器、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

**在修复之前**编写回归测试 —— 但仅当存在**正确的 seam** 时才这样做。

正确的 seam 是测试在调用点处像实际发生的那样行使**真实 bug 模式**的 seam。如果唯一可用的 seam 太浅（当 bug 需要多个调用者时的单调用者测试，无法复制触发 bug 的链路的单元测试），在那里的回归测试会给出虚假的信心。

**如果不存在正确的 seam，那本身就是发现。** 记下它。代码库架构正在阻止锁定 bug。标记此问题以供下一阶段使用。

如果存在正确的 seam：

1. 将最小化的复现转化为该 seam 处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 对原始（未最小化的）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 事后分析

声明完成之前需要：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或 seam 的缺失已被文档化）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 被证明正确的假设在 commit / PR 消息中陈述 —— 这样下一个调试者可以学习

**然后问：什么能防止这个 bug？** 如果答案涉及架构变更（没有好的测试 seam、纠缠的调用者、隐藏的耦合），将具体情况移交给 `/improve-codebase-architecture` 技能。在修复完成**之后**提出建议，而不是之前 —— 你现在比开始时拥有更多信息。
