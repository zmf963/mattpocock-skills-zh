# Codebase Design

设计**深度模块**（deep modules）：大量行为隐藏在小接口之后，放置在干净的 seam 处，通过该接口可测试。在任何设计或重构代码的地方使用这种语言和这些原则。目标是为调用者提供 leverage，为维护者提供 locality，为每个人提供可测试性。

## 词汇表

精确使用这些术语 —— 不要用"component"、"service"、"API"或"boundary"替代。一致的语言是全部意义所在。

**模块**（Module）— 任何有接口和实现的东西。刻意与规模无关：一个函数、类、包或跨层切片。*避免*：unit、component、service。

**接口**（Interface）— 调用者正确使用模块所需知道的一切：类型签名，还有不变量、顺序约束、错误模式、所需配置和性能特征。*避免*：API、signature（太窄 —— 它们只指类型层面的表面）。

**实现**（Implementation）— 模块内部的内容，其代码体。区别于**适配器**（Adapter）：一个东西可以是一个小适配器带一个大实现（一个 Postgres 仓库），或一个大适配器带一个小实现（一个内存 fake）。当 seam 是主题时使用"adapter"；否则使用"implementation"。

**深度**（Depth）— 接口处的 leverage：调用者（或测试）每学习一个单位接口就能行使的行为量。当一个模块的大量行为隐藏在小接口之后时，它是**深的**（deep）；当接口几乎和实现一样复杂时，它是**浅的**（shallow）。

**接缝**（Seam）*（Michael Feathers）* — 一个你可以改变行为而不在该处编辑的地方；模块接口所在的*位置*。将 seam 放在哪里是一个独立于其背后内容的设计决策。*避免*：boundary（与 DDD 的 bounded context 过载）。

**适配器**（Adapter）— 一个在 seam 处满足接口的具体东西。描述*角色*（它填充什么槽位），而不是实质（里面是什么）。

**杠杆**（Leverage）— 调用者从深度中获得的东西：每学习一个单位接口获得更多能力。一个实现在 N 个调用点和 M 个测试中回本。

**局部性**（Locality）— 维护者从深度中获得的东西：变更、bug、知识和验证集中在一个地方，而不是分散在调用者之间。修复一次，到处修复。

## 深 vs 浅

**深度模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← 少量方法，简单参数
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 隐藏的复杂逻辑
│                     │
└─────────────────────┘
```

**浅层模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 许多方法，复杂参数
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能在内部隐藏更多复杂性吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深度模块可以在内部由小的、可 mock 的、可替换的部分组成 —— 它们只是不是接口的一部分。一个模块可以有**内部 seam**（对其实现私有，由其自己的测试使用）以及接口处的**外部 seam**。
- **删除测试。** 想象删除模块。如果复杂性消失了，它就是透传。如果复杂性在 N 个调用者中重新出现，它就在赚取它的位置。
- **接口就是测试表面。** 调用者和测试穿过同一个 seam。如果你想测试*超越*接口，模块的形状可能不对。
- **一个适配器意味着假设的 seam。两个适配器意味着真正的 seam。** 除非某东西确实在它上面变化，否则不要引入 seam。

## 为可测试性设计

好的接口让测试变得自然：

1. **接受依赖，不要创建它们。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 更少的方法 = 需要更少的测试。更少的参数 = 更简单的测试设置。

## 关系

- 一个**模块**（Module）有且仅有一个**接口**（Interface）（它呈现给调用者和测试的表面）。
- **深度**（Depth）是一个**模块**的属性，相对于其**接口**来衡量。
- **接缝**（Seam）是**模块**的**接口**所在的位置。
- 一个**适配器**（Adapter）位于**接缝**处并满足**接口**。
- **深度**为调用者产生**杠杆**（Leverage），为维护者产生**局部性**（Locality）。

## 被拒绝的框架

- **深度作为实现行数与接口行数的比率**（Ousterhout）：奖励填充实现。我们改用深度作为 leverage。
- **"接口"作为 TypeScript 的 `interface` 关键字或类的公共方法**：太窄 —— 这里的接口包括调用者必须知道的每一个事实。
- **"Boundary"**：与 DDD 的 bounded context 过载。说**seam**或**interface**。
