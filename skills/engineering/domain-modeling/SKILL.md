# Domain Modeling

在设计时主动构建和打磨项目的领域模型。这是*主动*的纪律 —— 挑战术语、发明边缘情况场景、并在它们结晶的那一刻写下词汇表和决策。（仅仅*阅读* `CONTEXT.md` 获取词汇不是这项技能 —— 那是任何技能都能做的一行习惯。这项技能是用于当你正在改变模型时，而不仅仅是消费它。）

## 文件结构

大多数仓库有一个单一的上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，仓库有多个上下文。该 map 指向每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统范围的决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定的决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件 —— 只有当你有了要写的东西时才创建。如果不存在 `CONTEXT.md`，在第一个术语被解决时创建一个。如果不存在 `docs/adr/`，在第一个 ADR 需要时创建它。

## 会话期间

### 对照词汇表挑战

当用户使用一个与 `CONTEXT.md` 中现有语言冲突的术语时，立即指出。"你的词汇表将 'cancellation' 定义为 X，但你似乎意思是 Y —— 是哪一个？"

### 打磨模糊语言

当用户使用模糊或过载的术语时，提出一个精确的规范术语。"你说 'account' —— 你是指 Customer 还是 User？它们是不同的东西。"

### 讨论具体场景

当讨论领域关系时，用具体场景进行压力测试。发明探测边缘情况并迫使用户精确化概念之间边界的场景。

### 与代码交叉引用

当用户陈述某东西如何工作时，检查代码是否一致。如果你发现矛盾，提出来："你的代码取消整个 Orders，但你刚才说部分取消是可能的 —— 哪个是对的？"

### 内联更新 CONTEXT.md

当一个术语被解决时，立即更新 `CONTEXT.md`。不要批量处理 —— 在它们发生时捕获它们。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应该完全没有任何实现细节。不要将 `CONTEXT.md` 当作规格、草稿纸或实现决策的仓库。它是词汇表，仅此而已。

### 谨慎提供 ADR

只有在以下三个条件都成立时才提供创建 ADR：

1. **难以逆转** — 以后改变主意的成本是有意义的
2. **没有上下文会令人惊讶** — 未来的读者会想知道"他们为什么这样做？"
3. **真正权衡的结果** — 存在真正的替代方案，你出于特定原因选择了一个

如果三个中缺少任何一个，跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
