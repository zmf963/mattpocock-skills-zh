# Triage

将项目 issue 追踪器上的 issue 通过 triage 角色的小状态机移动。

如果此仓库将外部 pull request 视为请求表面（参见 issue-tracker 配置），triage 也覆盖它们：**PR 是附带代码的 issue** —— 相同的角色、相同的状态、相同的状态机，下面有一些标记为"对于 PR"的差异。根据追踪器配置将裸的 `#42` 解析为 issue 或 PR。

在 triage 期间发布到 issue 追踪器的每个评论或 issue **必须**以此免责声明开始：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写持久的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库如何工作

## 角色

两个**类别**角色：

- `bug` — 某些东西坏了
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 完全指定，准备好供 AFK agent 使用
- `ready-for-human` — 需要人类实现
- `wontfix` — 不会被处理

对于 PR，相同的状态针对附带的代码来解读：`ready-for-agent` 意味着附带了简报，agent 应该对 diff 采取下一步行动；`ready-for-human` 意味着它准备好供人类合并。

每个 triage 过的 issue 应携带恰好一个类别角色和一个状态角色。如果状态角色冲突，标记它并在做任何其他事情之前询问维护者。

这些是规范角色名称 —— issue 追踪器中使用的实际标签字符串可能不同。映射应该已经提供给你了 —— 如果没有，运行 `/setup-matt-pocock-skills`。

状态转换：未标记的 issue 通常先到 `needs-triage`；从那里移动到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 返回到 `needs-triage`。维护者可以随时覆盖 —— 标记看起来不寻常的转换并在继续前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解释请求并行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 显示需要关注的内容

查询 issue 追踪器并呈现三个桶，最旧的优先：

1. **未标记** — 从未 triage 过。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且自上次 triage 笔记以来有报告者活动** — 需要重新评估。

当 PR 在范围内时，在这些桶中包含外部 PR 并在每行标记 `[PR]` 或 `[issue]`。发现仅显示*外部* PR（追踪器配置定义谁算作外部）—— 协作者的进行中 PR 不是 triage 工作。此过滤器仅用于发现；显式命名的 PR 无论作者是谁都会被 triage。

显示计数和每个项目的单行摘要。让维护者选择。

## Triage 特定 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还有 diff）。解析任何先前的 triage 笔记，这样你不会重新问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域的 ADR。针对代码库运行两个检查：(a) **冗余** — 按领域概念（不仅是请求的措辞）搜索所请求行为的现有实现，并报告你在哪里查找的。如果找到，它是已实现的 `wontfix`（第 5 步）。(b) **先前拒绝** — 阅读 `.out-of-scope/*.md` 并提出来任何类似于此请求的内容。

2. **推荐。** 告诉维护者你的类别和状态推荐以及推理，加上与请求相关的简要代码库摘要 —— 包括是否已实现。等待指示。

3. **验证声明。** 在任何 grilling 之前，检查声明是否成立。对于 bug，从报告者的步骤复现它。对于 PR，确认 diff 做了它声称的事 —— checkout 它，运行相关测试或命令。报告发生了什么：已确认（附带代码路径）、失败、或细节不足（强烈的 `needs-info` 信号）。确认的验证产生更有力的 agent 简报。

4. **Grill（如果需要）。** 如果请求需要充实，一起运行 `/grilling` 和 `/domain-modeling` 技能 —— 一次一个问题地 grill 成形，打磨领域术语并在决策落地时内联更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发布 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 与 agent 简报相同的结构，但注明为什么不能委托（判断、外部访问、设计决策、手动测试）。
   - `needs-info` — 发布 triage 笔记（下面的模板）。
   - `wontfix` — 关闭，评论取决于*为什么*：
     - **已实现** — 变更已存在于代码库中。指向它所在的位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而不是已构建的）。
     - **已拒绝（bug）** — 礼貌解释，然后关闭。
     - **已拒绝（enhancement）** — 写入 `.out-of-scope/`，从评论中链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用角色。如果有部分进展，可选评论。

## 快速状态覆盖

如果维护者说"move #42 to ready-for-agent"，信任他们并直接应用角色。确认你将要做的（角色更改、评论、关闭），然后行动。跳过 grilling。如果移动到 `ready-for-agent` 而没有 grilling 会话，询问他们是否要编写 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

在"established so far"下捕获 grilling 期间解决的所有内容，这样工作不会丢失。问题必须具体和可操作，而不是"please provide more info"。

## 恢复先前的会话

如果 issue 或 PR 上存在先前的 triage 笔记，阅读它们，检查报告者是否已回答任何未解决的问题，并在继续前呈现更新的画面。不要重新问已解决的问题。
