一个松散的想法已经到达 —— 对一个 agent 会话来说太大，并且笼罩在迷雾中：从这到一个计划的路还不可见。此技能将其绘制为仓库 issue 追踪器上的**共享地图**（shared map），然后逐个处理其 ticket。地图是领域无关的 —— 工程工作、课程内容，任何适合该形状的。

## 按名称引用

每个地图和 ticket 是一个 issue，因此它有一个**名称** —— 其标题。在人类阅读的所有内容中 —— 叙述、地图的 Decisions-so-far —— 用该名称引用它，永远不要用裸 id、编号或 slug。一堆 `#42, #43, #44` 是不可读的；名称一目了然。id 和 URL 不会消失 —— 名称包裹其链接 —— 但它们位于名称*内部*，从不代替它。

## 地图

地图是此仓库 issue 追踪器上的单个 issue，标记为 `wayfinder:map` —— 规范产物。其 ticket 是地图的子 issue。

地图是**索引**，不是存储。它列出已做出的决策并指向持有其细节的 ticket；决策存在于恰好一个地方 —— 其 ticket —— 因此地图从不重述它，只摘要并链接。

**地图、其子 ticket、阻塞和前沿查询在物理上位于何处是追踪器特定的。** 查阅 `docs/agents/issue-tracker.md`（"Wayfinding operations" 部分）了解*此*仓库如何表达它们。如果该文档缺失，默认使用本地 markdown 追踪器。

### 地图正文

整个地图以低分辨率，每个会话加载一次。开放的 ticket **不**列出 —— 它们是开放的子 issue，通过查询找到。

```markdown
## Notes

<领域；每个会话应咨询的技能；此努力的固定偏好>

## Decisions so far

<!-- 索引 —— 每个已关闭 ticket 一行：足以判断相关性，然后缩放链接获取 ticket 持有的细节 -->

- [<closed ticket title>](link) — <答案的一行摘要>

## Fog

<!-- 参见 "迷雾" 了解什么属于此处 -->
```

### Ticket

每个 ticket 是地图的**子 issue**；追踪器的 issue id 是其身份。其正文是问题，大小适合一个 100K token 的 agent 会话：

```markdown
## Question

<此 ticket 解决的决策或调查>
```

两个标签系列：

- `wayfinder:<type>` — 以下之一：`research`、`prototype`、`grilling`、`task`（参见 [Ticket Types](#ticket-types)）。
- `wayfinder:claimed` — 会话在开始任何工作之前**首先**设置此标签，这样并发会话会跳过它。

阻塞使用追踪器的原生语义。当阻塞它的每个 ticket 都关闭时，ticket 是**已解除阻塞**的（unblocked）。**前沿**（frontier）是开放的、未阻塞的、未认领的子级 —— 已知的边缘。

答案不是正文的一部分 —— 它在解决时记录（参见 [Work through the map](#work-through-the-map)）。解决 ticket 时创建的资产从 issue 中链接，而不是粘贴进去。

## Ticket 类型

- **Research**：阅读文档、第三方 API 或本地资源如知识库。创建 markdown 摘要作为链接资产。当需要当前工作目录之外的知识时使用。
- **Prototype**：通过制作廉价、粗糙、具体的产物来提高讨论的保真度 —— 大纲、粗略尝试、存根，或通过 /prototype 技能的 UI/逻辑代码。将原型链接为资产。当"它应该看起来如何"或"它应该如何行为"是关键问题时使用。
- **Grilling**：与 agent 对话。使用 /grilling 和 /domain-modeling 技能。一次问一个问题。默认情况。
- **Task**：在讨论可以向前移动之前必须完成的文字性手动工作 —— 没有要决定的、没有要原型或研究的。移动数据、注册服务、配置访问权限。Agent 在可以的地方自动化它；否则它交给人类一个精确的检查清单。在工作完成时解决；答案记录做了什么以及后续 ticket 依赖的任何结果事实（凭证位置、新 URL、行数）。

## 迷雾

地图是*故意*不完整的：不要绘制你还看不到的东西。在 ticket 之外是迷雾（fog）—— 你能感觉到即将到来但还不能确定的决策和调查的朦胧视图，因为它们取决于仍然开放的问题。解决一个 ticket 清除它前面的迷雾，将现在可指定的任何东西提升为新的 ticket —— 一次一个，直到通往目标的道路清晰且没有 ticket 剩余。

地图的**Fog** 部分是写下那种朦胧视图的地方：怀疑的问题、稍后重新访问的区域、你正在推迟的风险。尽可能松散或完整地写下，取决于视图允许的程度；它也为阅读努力方向的协作者提供路标。

**迷雾还是 ticket？** 测试是你现在是否能精确地陈述问题 —— *不是*你现在是否能回答它。

- **Ticket 当**问题已经清晰 —— 即使它被阻塞且你还不能对其采取行动。
- **迷雾当**你还不能那么清晰地表述它。不要预先将迷雾切成 ticket 大小的碎片：它比 ticket 更粗糙，一片迷雾可能在前沿到达它时提升为几个 ticket，或没有。

迷雾仅排除已经决定的（那是 Decisions so far）和已经是 ticket 的。

## 调用

两种模式。无论哪种，**每个会话永远不要解决超过一个 ticket。**

### 绘制地图

用户以松散的想法调用。

1. 运行 `/grilling` 和 `/domain-modeling` 会话以揭示开放决策。
2. **创建地图**（标签 `wayfinder:map`）：Notes 已填写，Decisions-so-far 为空，Fog 已勾勒。
3. **创建你现在可以指定的 ticket** 作为地图的子 issue —— 然后在**第二轮**中连接阻塞边（issue 在相互引用之前需要 id）。连接将它们分类为前沿和已阻塞；你还不能指定的一切留在 Fog 中。
4. 停止 —— 绘制地图是一个会话的工作；不要也解决 ticket。

### 遍历地图

用户以地图（URL 或编号）调用。Ticket 是**可选的** —— 没有的话，你选择下一个决策，而不是用户。

1. 加载**地图** —— 低分辨率视图，不是每个 ticket 正文。
2. 选择 ticket。如果用户命名了一个，使用它。否则按顺序取第一个前沿 ticket。**认领它**：设置 `wayfinder:claimed` 并在任何工作之前保存。
3. 解决它 —— **按需缩放**：按需获取任何相关或已关闭 ticket 的完整正文；调用 `## Notes` 块命名的技能。如果有疑问，使用 `/grilling` 和 `/domain-modeling`。
4. 记录解决方案：将答案作为**解决评论**发布，**关闭** issue，并将**上下文指针**追加到地图的 Decisions-so-far。
5. 添加新浮现的 ticket（创建然后连接）；将答案使之可指定的任何迷雾提升，从 Fog 中清除每个提升的补丁，使其仅作为新 ticket 存在。如果决策使地图的其他部分无效，更新或删除那些 ticket。

用户可以并行运行未阻塞的 ticket，因此预期其他会话同时编辑追踪器。
